# UDP 遥测缺号诊断台

机房遥测出现缺号时，值班员用本工具判断**本机的 UDP 接收队列有没有溢出**：
本地发包端向本机 Linux 接收端发送一轮编号 UDP 包，每轮发完后留出收尾收包
时间，到期列出缺号，并读取**本轮接收套接字**的内核丢包计数，据此给出结论。

## 判定逻辑

| 缺号 | 内核丢包计数 | 结论 |
|---|---|---|
| 有/无 | > 0 | **本机 UDP 接收队列溢出**（计数随结论给出） |
| 有 | = 0 | 存在缺号，但**未发现本机接收队列溢出**（丢包在对端或链路） |
| 无 | = 0 | 链路完好 |
| — | 读不到 | **证据不足**（无法读取本轮套接字的内核计数） |

## 关键设计

- **每轮一个独立接收套接字**（127.0.0.1 临时端口）+ 独立发送/接收线程，
  多轮并发时计数天然互相独立、分别统计。
- **内核丢包计数来源：`/proc/net/udp` 的 drops 列**（即内核按套接字维护的
  `sk_drops`：报文到达时本机接收队列已满而被丢弃的次数）。建套接字时读基线、
  收尾时读终值，本轮计数 = 终值 − 基线。
  - 为什么不用标准的 `getsockopt(SO_RXQ_OVFL)`：实测目标内核（Linux 7.0.0）
    该路径只返回开关状态（开=1/关=0），灌包产生 2997 个丢包读数不变；
    同一计数经 procfs 的 drops 列暴露且随丢包正确递增，故以 procfs 为准。
- 报文格式：`magic(4B) | 轮次令牌(4B) | 编号(4B) | 填充`，接收端按令牌过滤，
  杜绝并发轮次之间串台。

## 网页演示

- **「并发演示」按钮**：同时开跑两轮 ——
  - 暂缓轮：小接收缓冲（4 KiB）+ 接收端暂缓 600 ms 收包 → 队列积压，
    内核丢包计数 > 0 → 判定**本机队列溢出**；
  - 跳号轮：发送端主动跳过编号 500–549 → 缺号 50 个但计数为 0 →
    判定**未发现本机溢出**。
  两轮同跑、分别出数，直观展示并发统计互不干扰。
- **自定义一轮**：可调包数、包长、发送间隔、接收暂缓、每包处理耗时
  （`recv_delay_ms`，模拟业务处理慢造成的积压）、收尾时间、接收缓冲
  （`rcvbuf`，调小更容易溢出）、发送跳号（如 `10,20,30-40`）。

## 测试与实测结果

```bash
cd app && python3 -m pytest test_rounds.py -v     # 8 项全部通过
```

在 Linux 7.0.0 环境实测：

- 干净轮（800×256B，大缓冲）：缺号 0，计数 0 → 链路完好；
- 跳号轮（跳 500–549）：缺号恰为 500–549 共 50 个，计数 0 → 未发现本机溢出；
- 暂缓轮（4 KiB 缓冲 + 暂缓 600 ms，4000×1000B）：缺号 3997，计数 3997 → 本机队列溢出；
- 每包处理 2 ms 轮（8 KiB 缓冲，3000×1000B）：缺号 2984，计数 2984 → 本机队列溢出；
- 并发演示：两轮同时跑，各自端口、各自计数，互不影响；
- 计数读不到（测试中用 mock 模拟）：结论为「证据不足」。

## 限制与说明

- 诊断依赖 Linux procfs（`/proc/net/udp` 需有 drops 列）；非 Linux 或读不到
  时按规则报「证据不足」。容器内 `/proc` 即本网络命名空间视图，无需特权。
- 收尾判定以「发完 + grace 到期」为准：若把 `recv_delay_ms` 调得很大，
  到期的瞬间队列里可能还有没取走的包，这些会计入缺号——这是"到期列缺号"
  的既定语义，值班员可通过加大 `grace_ms` 规避。
- 计数是"本轮套接字生命周期内"的增量（终值 − 基线），不含其他轮次/其他
  套接字；但它只覆盖**本机接收队列溢出**这一类丢包，不证明链路或对端无丢包。
- Flask 内置服务器面向诊断演示场景，未做鉴权，请勿暴露到不可信网络。
